# 產物記錄、保留與回放支援：共同理解

狀態：2026-10-30 使用者已確認整體共同理解，授權整理[正式規格](../../.scratch/archive/artifact-recording-and-retention/spec.md)與[任務](../../.scratch/archive/artifact-recording-and-retention/README.md)，並明確要求先不實作。本摘要為設計背景，實作需求以正式規格為準。完整依據見[訪談 Q1–Q19](artifact-recording-and-retention.md)。

## 目標與範圍

環境快速演進期間，降低完整記錄、歷史回放相容及舊產物保留的成本。使用者主要從模擬畫面看現象；資料供 Codex 或其他 LLM 後續分析，不供專案內生物 AI 使用，也不自動呼叫 LLM。

本輪涵蓋記錄預設、完整錄製、回放支援、保留與清理及相關文件／驗收調整。六場生態觀察、果實產量調整、幼體照顧長期對照、PPO 與混合控制實驗維持原狀。

## 日常資料與完整錄製

| 情境 | 已確認行為 |
| --- | --- |
| 日常執行 | 保存精簡結果摘要、每一模擬秒的群體統計及來源資訊，不保存逐步個體完整狀態。 |
| LLM 讀取 | 先讀人口、營養、來源與果實供給的起訖、變化範圍、累計出生死亡／果實流量及停止原因；需要時再查時間序列。事件累計不能因低頻寫檔漏算。 |
| 來源資訊 | 保留配置、種子、控制方式及可辨識實際程式建置的資訊；規則名稱不能取代建置識別。 |
| 完整錄製 | 啟動前明確開啟，涵蓋該次啟動至停止的所有世界輪次，重建時分段；不增加執行中錄製開關。 |
| 正常提前停止 | 已錄到的連續片段可播放，區分觀察提前停止與世界輪次自然結束。 |
| 成功封裝 | 所有必要分段通過檢查，且需保留的資訊已另存後，才移除冗餘來源並取代上一份成功錄製。 |
| 異常資料 | 崩潰、強制終止或寫入失敗不新增搶救或殘缺回放播放；保留已寫入資料，依保留規則淘汰。 |
| 記錄寫入失敗 | 初始化時無法建立記錄則啟動失敗；執行中才失敗則停止此次記錄、標示不完整，世界與畫面繼續，不算資料驗收成功。 |

## 回放支援與保留

- 只保證產生回放的同一份建置可播放；不同建置明確拒絕，即使規則版本名稱相同。退役 v9–v14 專用讀取／轉換與歷史回放驗收，不遷移舊資料。
- 同建置保留最近五次已停止執行的輕量資料，包括失敗場次；另保留最近一次成功完整錄製及其必要摘要／來源資訊。一次錄製包含該次執行的所有分段，不能只保留最後一輪。
- 新錄製失敗不取代上一份成功錄製；失敗來源隨所屬執行淘汰。仍在執行或播放中的資料暫不清理。
- 新建置成功且成為日常使用版本後，自動淘汰舊建置的模擬產物；建置失敗不觸發。五次／一次的保留數量不是跨建置豁免。
- 過期範圍包括模擬統計、來源資訊、回放、日誌、失敗殘檔及原始驗收素材；長期結果保留在 Git 正式文件與報告。現行測試所需素材須先妥善安置，環境、工具快取及模型另行管理。

## 程式與 LLM 的清理分工

- 程式在建置／執行流程套用固定規則，只管理專案內專用模擬產物目錄中的可識別資料；不增加常駐清理服務。
- LLM 負責首次辨識舊資料、處理測試依賴與文件引用，以及後續規則調整。首次淘汰不等於清空整個 artifacts。
- 自訂輸出或另存複本不自動追蹤刪除，也不承諾跨建置可播放。
- 開發需跨建置或多場比較時，LLM 在觸發淘汰前另存本次任務所需資料。分析後將有效結果整合至正式文件並清除臨時大檔；不增加永久釘選功能。

[fruit-supply-and-flow](../../.scratch/fruit-supply-and-flow/README.md) 的 11 保留原完成與驗收紀錄；本次使用者回報的相容問題未重現或修復。新規格將取代未來歷史相容承諾，不能反過來改寫當時證據。

12／13 保持 deferred；本輪不自動恢復六場觀察，不將其視為通過，也不提前結案歸檔。新政策落地時須同步調整失效的舊版驗收要求及引用，保留其他尚未完成工作。

## 後續規格與驗收重點

依上述行為整理本機正式規格與任務，涵蓋日常輕量輸出及統計正確性、同建置多輪錄製／跳轉、提前停止、不同建置與損壞資料拒絕、記錄失敗隔離、整批錄製成功判定、五次／一次保留、建置切換與管理範圍，以及首次舊資料處置。技術上的建置識別方式、檔案結構與清理實作由上述行為約束，不增加跨建置相容或自動 LLM 分析能力。
